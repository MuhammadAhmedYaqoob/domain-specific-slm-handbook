# Parameter-efficient fine-tuning (PEFT) methods

## Scope and evidence policy

This initial survey covers every parameter-efficient fine-tuning (PEFT) method named in `prompt.txt`. Research was
checked on 2026-11-23 against original papers, official repositories, and current Hugging Face PEFT documentation.
`PAPER-REPORTED` means the result or characterization comes from the cited paper and has not been reproduced in this
project; `DOC-VERIFIED` means the API or support statement was present in current documentation, not that it ran
successfully here. All model-, task-, precision-, and hardware-specific outcomes remain `TEST-REQUIRED`.

PEFT primarily reduces trainable state and per-domain artifact size. It does **not** automatically reduce the frozen
backbone's inference memory, compute, or KV cache. Merged low-rank adapters can avoid adapter execution overhead, but
the resulting dense model normally retains the base architecture and parameter count.

## Lesson: adapting a model without retraining every weight

### Problem and intuition

Full fine-tuning stores gradients and optimizer state for a large fraction of the model and produces another full
checkpoint for each domain. PEFT methods were developed to make adaptation cheaper by freezing the pretrained backbone
and learning a small control surface. The intuition is similar to adjusting selected controls on an existing machine
instead of rebuilding it. The machine remains the same size at inference unless a separate compression step follows.

### Mechanisms and historical progression

Prompt tuning learns virtual input tokens; prefix methods inject learned state into multiple layers; bottleneck adapters
insert small neural modules; IA3 rescales activations; BitFit updates biases; and Low-Rank Adaptation (LoRA) learns
low-rank matrix updates. LoRA became the dominant practical baseline because linear layers are common, adapters are
small, and additive updates can often be merged. Quantized LoRA (QLoRA) later reduced training memory by keeping the
frozen base in a 4-bit representation while training LoRA parameters.

### Worked illustrative comparison

For a 1B automotive base model, compare full fine-tuning, attention-only LoRA, all-linear LoRA, and QLoRA on identical
accepted training tokens. Full fine-tuning is the adaptation-capacity control. Attention-only LoRA minimizes adapter
state but may underfit terminology and procedures represented in feed-forward layers. All-linear LoRA adds capacity.
QLoRA asks whether similar learning can fit a smaller training-memory budget. After training, merge the selected
adapter, verify output parity, and quantize separately for the phone runtime. This example intentionally states no
benchmark outcome.

### When to use or avoid

Use LoRA as the first reproducible multi-domain adapter baseline. Use QLoRA when accelerator memory is the binding
training constraint and the bitsandbytes path supports the exact modules. Use prompt/prefix techniques when tiny,
switchable artifacts matter more than context and runtime overhead. Avoid advanced variants until a controlled baseline
shows the problem they claim to solve. Avoid claiming edge compression from PEFT alone.

The foundational table shows increasing adaptation capacity and deployment complexity, not a universal ranking. BitFit
and prompt methods are useful cheap controls. IA3 is compact but architecture-sensitive. Bottleneck and prefix methods
can add runtime operations. Full fine-tuning establishes what is lost when updates are constrained; it remains expensive
and can increase forgetting.

## LoRA family

For a frozen weight \(W\), LoRA learns \(\Delta W = sBA\), where rank \(r\) is much smaller than the input/output
dimensions. Rank, scale, target modules, dropout, initialization, optimizer, and data are coupled experimental
variables.

The LoRA table should be interpreted by mechanism. rsLoRA changes scaling, LoRA+ changes optimization, and
PiSSA/OLoRA/EVA change initialization or allocation; none automatically changes the final dense model size. DoRA adds a
magnitude component. LoftQ addresses quantized fine-tuning initialization but is not a general mobile quantizer.
Compatibility means more than an available configuration flag: target modules, base mutation, merge metadata,
distributed training, and exporter behavior must all survive an exact end-to-end test.

## Adapter composition and deployment

- **Stacking:** sequential adapters can represent multiple transformations but add operators and latency. Support is
  framework- and adapter-type-specific; measure rather than assume.
- **Fusion/composition:** methods such as AdapterFusion (Pfeiffer et al., EACL 2021,
  [paper](https://aclanthology.org/2021.eacl-main.39/)) learn to combine trained adapters. This is useful when domains
  overlap, but it introduces another training stage and does not guarantee conflict-free knowledge.
- **Merging:** additive LoRA-like updates can usually be folded into dense weights. Merge in a high-enough precision,
  validate outputs, then quantize for the target runtime. Quantized in-place merge support varies.
- **Multi-adapter serving:** efficient in cloud systems when the runtime explicitly batches/routs adapters. On mobile,
  one merged artifact per released domain is operationally simpler unless the selected runtime has tested adapter
  loading.

## Initial project decision

1. **Core baseline:** full fine-tuning where feasible, LoRA, and QLoRA on the same base checkpoint and dataset.
2. **First ablations:** target attention versus all-linear modules; rank; rsLoRA; DoRA; LoRA+.
3. **Conditional experiments:** LoftQ for bitsandbytes QLoRA; EVA for domains with enough representative calibration
   data; PiSSA when initialization cost is acceptable.
4. **Research-only initially:** OLoRA and complex stacking/fusion until provenance, merging, and edge export are
   demonstrated.

No method should be selected from paper headline results. For each candidate, record exact base revision, tokenizer/chat
template, target modules, rank/scale/dropout, trainable count, precision, optimizer groups, seeds, peak training memory,
domain evaluation, general-retention evaluation, merged-output equivalence, and final runtime compatibility.
